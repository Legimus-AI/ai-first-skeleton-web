# i18n (Locale Awareness)

The UI is Spanish (Peru, `tú`): `<html lang="es">`, Zod validation messages are configured once in `src/main.tsx` (`z.config` with `z.locales.es()` plus plain copy for the common cases), and API errors reach the user only through `toUserMessage` (see [api-client.md](api-client.md)). Dates use `formatDate`, `formatDateTime` and `formatRelative` from `@/services/date-format-service` (a service, not a `utils/` helper: it holds the runtime preferences); slices never format dates themselves (INV-112).

## Locale and time zone come from the account

Dates follow the runtime settings ([ADR 0024](https://github.com/Legimus-AI/ai-first-architecture/blob/main/docs/decisions/0024-runtime-settings-per-organization-and-user.md)), not the build:

| What | Signed in | Outside the signed-in shell (login, sign-up, email links, `_session/*`: OAuth consent, CLI approval) |
|------|-----------|----------------------------------------------|
| Locale (date format) | The organization's `locale` (`GET /api/v1/organization/settings`) | `VITE_LOCALE` (default `es-PE`) |
| Time zone | The person's `timeZone`, or the organization's when they chose none (`GET /api/v1/me/settings`) | The browser's zone |

- The `_authed` route's `loader` loads both documents (in parallel) and calls `setDateFormatPreferences({ locale, timeZone })` before any signed-in page renders, so a table never shows a date in the wrong zone first.
- Both documents never go stale on their own (`staleTime: Infinity`) and are not refetched on window focus, so one page never mixes two zones; only a save changes them (the forms on `/settings/general` and `/settings/preferences` put the API's answer in the cache).
- `useSettingsSync` (`src/slices/settings/hooks/use-settings-sync.ts`, called by the `_authed` route component outside the layout) applies them again whenever either document changes, and `resetDateFormatPreferences()` puts the build locale and the browser's zone back when the shell unmounts (sign-out, or a `_session/*` page such as `/oauth/consent` or `/device`).
- `formatDate` and `formatDateTime` pass `timeZone`, so the calendar day and the hour are the account's: an instant at 20:00 UTC is the 12th in `America/Lima` and the 13th in `Pacific/Kiritimati`. `formatRelative` counts elapsed time ("hace 2 horas"), which no zone changes; past a week it shows `formatDate`.
- Only the server validates a zone; replies carry it as plain text. When this browser's `Intl` cannot format the effective zone (its tz data is older), `setDateFormatPreferences` logs it with `console.error`, keeps the locale and formats in the device's zone; `useSettingsSync` shows the warning once as a toast on any page, and both settings pages keep it visible (`getUnsupportedTimeZone`, `useUnsupportedTimeZone`).
- The supported locales are `SUPPORTED_LOCALES` in `@repo/shared`. They change formats only: the copy stays Spanish.

**Rules:**

- **Never hardcode a locale or a zone** and never read `VITE_LOCALE` for display: go through `@/services/date-format-service`, which holds the runtime preferences.
- **Numbers:** the skeleton formats none yet. A number formatter belongs next to the date formatters in that service and must take the same runtime locale (extend `setDateFormatPreferences`), not `VITE_LOCALE`.
- **Text direction:** components should support `dir="rtl"` for future RTL locales (avoid hardcoded `left`/`right`, use `start`/`end` in Tailwind).

## Theme

The person's `theme` (`light | dark | system`) is saved in `user_settings` too. `localStorage` stays the first-paint cache (`index.html` applies it before React loads). On the first load of a session the account's theme wins over that cache; after that, every change from any toggle (the header button, `ThemeToggle`, the segmented control on `/settings/preferences`) is saved once by `useSettingsSync` through `useSaveTheme` (optimistic, one save at a time). No success toast: the theme changing on screen is the feedback. If a save fails, "No pudimos guardar el tema. Intenta de nuevo." shows and the last theme the server confirmed comes back on screen (unless a later toggle replaced it), so the tab and the account agree. When another account signs in from another tab, its theme applies once its settings arrive. The notification-sound switch on `/settings/notifications` still lives only in `localStorage`; it is not an account setting.

## Not Included (Future)

This skeleton provides locale awareness for formatting only. Multi-language support requires:
- Translation files (e.g., `i18next`, `react-intl`)
- Language switcher component
- Route-level locale detection
